# BENCHMARK — measured accuracy vs the oracle crosswalks

This is the repo's measured-accuracy record: dbz's computed overlaps scored against the
production-derived **overlap oracle** combination crosswalks that ship in
`cross-mapping/core-audit/mappings/` and `overlap-data/` (designated ground truth in
`CLAUDE.md`). Numbers are produced by `cross-mapping/tests/benchmark_oracles.py`, which reuses
the canonical ER parser (`cross-mapping/engine/er_overlap.py`) — no second parser, no
reinterpretation of the data.

## What is measured

**Layer 1 — ER-level (audit-request granularity).** For each oracle pair, the shared-ER set the
engine computes from the primary crosswalk is scored against the oracle's authoritative shared
set: precision, recall, F1. This validates the ER overlap engine end to end.

**Layer 2 — spine-level (native-control granularity).** The native control ids the production
oracle co-cites with SOC 2 are scored against the ids on dbz's `master_mappings` edges for the
same pair:

- **Oracle coverage** — the fraction of oracle-co-cited ids the spine recovers. A true recall
  against ground truth.
- **Corroboration rate** — the fraction of the spine's edge ids the oracle co-cites. This is
  deliberately **not** called precision: the oracle is one production sample, so a spine edge
  absent from it is *unconfirmed*, not wrong.

## Honest scope limits

- Oracle coverage is partial: the oracles span the SOC 2 / ISO / HIPAA / HITRUST commercial
  core, not the federal side (800-53, FedRAMP, CMMC have no production oracle here).
- The oracles are production-derived: they inherit their compiler's judgment and scope (the
  HITRUST oracle is e1-scoped, so the engine computing a superset is expected and the layer-1
  precision figure for that pair carries that caveat).
- SOC 2 × HIPAA Security has **no layer-2 row by design**: the oracle's HIPAA side carries
  provider-proprietary identifiers, which never leave their mapping directories (publication
  hygiene). Only aggregate counts appear in this document and in the benchmark output.
- The SOC2×ISO spine edges are consensus-tier; layer-2 coverage therefore measures the
  consensus surface specifically, which is held to its own (lower) pin than the ER layer.

## Hub-vs-authority corroboration (phase 36 measured, phase 37 extended)

Where a framework carries BOTH hub coverage and an authoritative mapping under the same
canonical label, the hub method can be scored against the authority. Phase 36 found only one
such comparison existed; phase 37's identifier fix (finding F-7) created a second and much
larger one. Restricted to native ids both sides cover:

| Framework | Authority | Shared ids | Hub recall of authority | Hub corroboration | Fan-out |
|---|---|---|---|---|---|
| HIPAA Security | NIST SP 800-66r2 OLIR | 52 | 0.762 | 0.026 | 29.6x |
| NIST SP 800-171 r2 | CMMC/800-171 crosswalk | 313 | 0.744 | 0.034 | 21.6x |

**Read these correctly.** *Corroboration* is deliberately not called precision: these
authorities are SELECTIVE mappings, so a hub edge they omit is **unconfirmed, not wrong**. What
the pair of rows does establish, consistently across two independent frameworks, is that the
hub asserts 20-30x more relationship than the authority agrees with, while recovering roughly
three quarters of what the authority states.

**Conditional adjudicated figure.** Phase 36 adjudicated a seeded sample of hub edges against
source text: **63.2% UNSUPPORTED (n=38 decidable, 95% CI [47.9%, 78.5%])** versus 25.0% for
authoritative control strata (two-proportion z = 2.32, p ~ 0.02). This figure is **conditional
on the strong reading** of what an edge claims — "doing X contributes to satisfying Y". Under
the weak reading ("X and Y concern related subject matter") most of those edges are defensible.
That ambiguity is exactly what the `edge_semantic` column (schema 3.15) now resolves per edge.
The labeler also built the pipeline; the seeded sample keys are recorded for independent
re-labeling. Full method and limits: `docs/audits/phase-36-master-accuracy-audit.md`.

## Framework → CCI confirmation (phase 38)

The repository's objective is convergence onto **confirmed CCI mappings**. Verdicts are derived
from independent witnesses (`cci_confirm.py`; vocabulary in `framework_vocab.json →
cci_confirmation`), measured 2026-08-13 over **478,610** framework→CCI pairs:

| Verdict | Pairs | Meaning |
|---|---|---|
| `confirmed` | **53,046** | CCI anchor multi-witness confirmed + ≥2 agreement witnesses, ≥1 CCI-level |
| `corroborated` | 81,933 | anchor confirmed + exactly one agreement witness |
| `reachable` | 286,642 | transitive join only — **not a mapping** |
| `weak` | 56,989 | the CCI's own anchor is `disa_only`/`candidate` |

Per framework (`confirmed`): NIST SP 800-171 r2 **23,003** · HIPAA Security **25,231** ·
ISO 27001/2 (2022) 1,936 · CIS CSC v8.0 1,399 · PCI DSS v4.0 1,136 · NIST CSF 2.0 341.
Frameworks with a single mapping publisher and no STIG-exercised CCIs cap at `corroborated`
by construction — CSA CCM, GDPR, CMMC 2.0 and FedRAMP r5 show 0 confirmed, which is the honest
ceiling of their current evidence, not a defect.

**Witness independence** is the load-bearing property: a second publisher on the same anchor, a
STIG rule that actually exercises the CCI, and another framework agreeing via consensus are
different kinds of evidence. The consensus witness matches at control granularity, so it may
support a confirmation but can never carry one alone — `validate_spine` check 19 enforces that,
along with the rule that a `confirmed` row's CCI anchor must itself be confirmed. Floor pinned
at 40,000 (measured 53,046).

## Regression policy (measure-then-pin)

Thresholds in `benchmark_oracles.py` (`MIN_LAYER1` / `MIN_LAYER2`) are pinned 2–3 points
**below** the measured values recorded above, so `--check` catches real regressions without
flapping on noise. Pins are never aspirational — a pin above measured reality would be a
fabricated claim. When data legitimately changes (a source re-pin, a new oracle), the
procedure is: re-measure → re-pin → record the change in the changelog. Pins are never
deleted.

`--check` runs in the `standards-watch` CI workflow after a fresh database build (it needs a
built `grc.db` plus pandas, which that workflow installs; the dependency-free `health` workflow
does not run it). Locally it belongs to the full gate battery described in
`docs/standards-refresh-runbook.md`.
